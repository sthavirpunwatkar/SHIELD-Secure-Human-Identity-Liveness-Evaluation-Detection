# SHIELD Root Cause Investigation Report
**Issue:** rPPG Confidence = 0.0000 (Regression)
**Severity:** Critical
**Confidence Level:** High

## 1. Observed Symptom
During live verification sessions, the `rPPG Confidence` consistently drops to exactly `0.0000` (as seen in the breakdown logs), artificially penalizing the overall liveness score and causing valid, live users to be rejected.

## 2. Earliest Failing Stage
The earliest component that produces the incorrect data is the initialization gate inside the `update()` method of `inference/rppg_detector.py`. 

## 3. Exact Root Cause
The root cause is a **post-processing logic error combined with a system integration failure**, not a neural network failure.

1. **Hardcoded Buffer Return**: In `RPPGDetector.update()`, there is a hardcoded rule:
   ```python
   if len(self.signal_buffer) < self.window_size:
       return 0.0
   ```
   This explicitly returns `0.0` for the first 149 frames (which equates to 5 seconds at 30 FPS).
2. **Fusion Engine Penalization**: `FusionEngine.fuse()` does not ignore the `rppg_score` while the buffer is filling. It blindly includes the `0.0` in the weighted sum (e.g., `0.40 * 0.0`), pulling down the `final_score` and logging `"rppg": 0.0000` in the breakdown.
3. **Session Timeout vs. Fill Rate**: The frontend captures frames at a lower FPS (e.g., 2 FPS). At 2 FPS, it requires **75 seconds** to fill the 150-frame buffer. However, `ChallengeSession` timeouts are capped at 5 seconds per challenge. Consequently, the buffer **never** reaches 150 frames before the session expires. The system is trapped in a permanent initialization state, perpetually emitting `0.0000` for every frame of every live user.

*Note: This was introduced as a regression during a previous PR fix (PR-0055). Test cases like `test_fusion_pipeline.py` confirm this: `"Before the fix, rppg_score was defaulting to 0.5 when initializing. We test the new fixed state where rppg_score = 0.0"`.*

## 4. Model Output & Confidence Validation
To scientifically prove that the model itself is not producing the `0.0000` score on live faces, I wrote test harnesses (`test_real_video.py`, `test_bandpass_noise.py`, `test_zero.py`) to bypass the `buffer < window_size` logic and execute the ONNX INT8 model directly:
*   **Real Human Signal (150 frames)**: The ONNX model successfully outputs `~0.975` confidence.
*   **Bandpassed Random Noise (Jitter)**: Outputs `~0.988` confidence (because the bandpass filter smooths the noise into a sinusoidal shape).
*   **Perfectly Flat Signal (Static Spoof Photo)**: Only a perfectly static tensor with no variance (standard deviation exactly 0.0) causes the ONNX model to output `7.92e-05`, which rounds to `0.0000`.

**Conclusion**: The neural network behaves correctly and outputs high confidence for live signals. The `0.0000` is entirely artificially generated by the Python post-processing block when `len(buffer) < 150`.

## 5. Training vs. Inference Differences (Parity)
While exploring the root cause, a separate parity mismatch was verified between training and inference:
*   **Training (`train_rppg_v2.py`)**: Models are trained on noisy physiological signals that are Z-score normalized but **not** bandpass filtered.
*   **Inference (`rppg_detector.py`)**: Inference applies a `filtfilt` Butterworth bandpass (`0.7 - 4.0 Hz`). 
*   **Impact**: Although this mismatch exists and fundamentally alters the input distribution, it actually biases the model toward *higher* false-positive confidences (since bandpassed noise resembles a clean cardiac wave), meaning it does *not* cause the `0.0000` symptom.

## 6. Recommended Fix (Description Only)
The fix requires correcting how the `FusionEngine` handles the unready state of the rPPG buffer.
1. **Dynamic Fusion**: Modify `FusionEngine.fuse()` to dynamically re-weight the modalities. If `rppg_ready == False`, the engine should completely ignore the rPPG component (distributing its 30-40% weight across the `blink` and `antispoof` scores) rather than incorporating a penalizing `0.0`.
2. **Buffer Alignment**: Ensure `rppg_detector.py` returns `None` or `NaN` (instead of `0.0`) when the buffer is incomplete, allowing the `FusionService` to explicitly detect and handle the unready state safely.
3. **Frontend FPS Parity**: Long-term, the `window_size` must be calibrated to the actual frontend capture rate to ensure the buffer can realistically fill within a 5-second challenge window.
